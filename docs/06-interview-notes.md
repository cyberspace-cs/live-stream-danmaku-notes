# 06 · 面试怎么讲这个项目

## 一、先把数字口径说清楚（最重要）

面试官听到「150 万 QPS」第一反应是怀疑。你要**主动拆口径**，而不是等他质疑：

> 「150 万是**下行投递次数**，不是 150 万条独立弹幕。6 万在线连接，假设每秒产生 25 条弹幕，每条要投递给同房间的所有连接，投递次数就是 150 万。Redis Publish 的次数其实只有 25 次/秒，瓶颈在单机的 write 系统调用和网卡，不在 Redis。」

这句话一出， credibility 立刻不一样。相反，如果你说「我的系统每秒处理 150 万条弹幕」，被追问「Kafka 单分区能写 150 万？」就崩了。

同理，「2.5 万 QPS 上行」= 每秒 2.5 万次 `Publish + Produce`，也是可以自洽的。

## 二、STAR 结构（90 秒版本）

**S（背景）**：直播弹幕看起来简单，实际有四个硬问题——几十万长连接怎么扛、一条弹幕怎么实时扇出给几万人、瞬时百万条怎么不把 MySQL 打死、分布式下在线人数和点赞数怎么准。

**T（任务）**：用 Go + Redis + Kafka + MySQL 从零做一个能跑出真实压测数据的后端，目标单机 6 万连接。

**A（行动）**：四层设计——

1. **接入层**：Go 协程 per connection，Gorilla WebSocket，Read/Write 双泵分离。
2. **广播层**：Manager 维护 `房间 → 客户端集合`，100 个 worker 消费 job 队列，客户端各有 4096 缓冲，满了丢弃不阻塞；切片用 sync.Pool 复用。
3. **跨机层**：Redis Pub/Sub 按房号分频道，每个实例每个房间一个订阅协程；注意**本地也走 Redis 回环**，避免重复广播。
4. **持久化层**：Kafka Async Producer 削峰，Consumer Group 攒批 2 秒或满批写 MySQL；消费端用 channel 做背压。

**R（结果）**：6 万连接、150 万下行投递/秒、2.5 万上行/秒、丢包 < 1%、500 万积压 2 分钟落盘。

## 三、四个难点的标准答法

### 难点 1：几十万长连接，服务器怎么扛？

> 「Go 的 goroutine 初始栈 2KB，6 万连接大约占 120MB 栈空间，加上内核每个连接的 socket buffer（约 4~8KB），总共 500MB 左右，一台 8G 机器很轻松。真正的瓶颈是 **fd 数量和本地端口**：服务端要 `ulimit -n`，客户端压测时受 `ip_local_port_range` 限制，默认只有 2.8 万个端口，所以 6 万连接必须扩端口范围或者压测机加多 IP。」

**加分点**：提一句「如果连接数上到百万级，单机 goroutine 模型还能撑，但 GC 扫描和调度延迟会变成问题，那时候要考虑多进程 + SO_REUSEPORT，或者用 epoll 自己做事件循环（比如 gnet）」。

### 难点 2：广播风暴怎么解？

> 「核心是**不要在发送方扇出**。用户发一条弹幕，服务端只做两件事：写 Kafka、Publish 到 Redis 的房间频道，然后立刻返回。真正的扇出发生在每个实例的订阅协程里——它拿到消息后，先把房间的客户端集合**拷成一个切片**（持读锁，只拷指针，5 万个约 0.2ms），解锁，然后把「切片 + payload」打包成一个 job 丢进队列，100 个 worker 并发消费，每个 worker 遍历切片做非阻塞投递。」

**追问「为什么不在本地直接广播，还要绕一圈 Redis？」**

> 「因为如果本地直发 + Redis 广播同时做，本机用户会收到两条。只保留 Redis 回环这一条路径，代码没有分叉，也不会重复。代价是本机多一次 Redis 往返，大概 0.5ms，对弹幕场景可以接受。」

### 难点 3：瞬时百万条弹幕，MySQL 怎么不崩？

> 「上游用 Kafka 做缓冲池，Async Producer 配 Snappy 压缩、50 条/50ms/8KB 三条件触发批量发送，`RequiredAcks=WaitForLocal` 只要 leader 确认。下游 Consumer Group 把消息先塞进一个 2000 容量的 channel，独立的 dbWorker 协程攒够 batchSize 或者 2 秒超时，用 GORM 的 CreateInBatches 一条 SQL 插 N 行。channel 满了会阻塞 Kafka 消费，形成天然背压，不会把内存撑爆。」

**加分点**：主动说「这里我做的是 at-most-once——入队就提交 offset，如果此时进程崩了会丢一批。要严格不丢，得把提交推迟到落库之后，再用唯一索引做幂等。」

### 难点 4：分布式下在线人数和点赞数怎么准？

> 「在线人数用**心跳覆盖写**，不用 INCR/DECR。每个实例每 3 秒把自己房间的在线数 `SET key count EX 7` 写进 Redis，同时把自己加到一个 Set 注册表里；聚合的时候 `SMembers` 拿实例列表，`MGet` 拿各自的数求和，读到 nil 就说明那个实例挂了，顺手 `SRem` 清掉。这样进程被 kill -9 也不会让数字永久虚高，最多 7 秒自愈。
>
> 点赞用**本地聚合**：每次点赞只加内存计数器，3 秒一次交换 map 出来批量 `INCRBY`。热门房间点赞 10 万 QPS，聚合后写入量降了几个数量级。」

## 四、追问防御清单

| 追问 | 怎么答 |
|------|--------|
| **Redis 挂了怎么办？** | 广播链路直接断（Pub/Sub 无持久化）。生产要把 Redis 做成主从 + Sentinel，或者降级为「只写 Kafka，客户端轮询拉取」，牺牲实时性保可用。 |
| **消息会丢吗？** | 会。Pub/Sub 断线期间的消息不补发；消费端 at-most-once。生产换 Redis Stream + 幂等落库可以做到不丢不重。 |
| **消息顺序怎么保证？** | 不保证跨消息顺序。100 个 worker 并发处理不同 job，A、B 两条弹幕可能颠倒。同一条消息对所有客户端是一致的。要严格有序得按 roomID hash 到固定 worker。 |
| **怎么水平扩容？** | Server 完全无状态，直接加实例。但扩容会放大 Redis 出口流量（每个实例都要收全量广播），所以真正的瓶颈是 Redis 带宽，需要按 roomID 分片到多个 Redis 实例。 |
| **100 万人的房间怎么办？** | 单实例扇出 100 万次，每秒 1 条就是 100 万次 write，单机扛不住。要分层：按客户端连接 hash 分成多个「扇出子集群」，每个子集群只负责一部分连接，Redis 按子集群再分频道。 |
| **为什么不用 Kafka 直接做广播？** | 可以，而且更可靠。Kafka 每个消费者组独立消费，天然支持多实例扇出。不用是因为延迟更高（攒批 50ms + 拉取间隔），弹幕要求秒级内送达。实际 B 站是「Kafka 存储 + 自建长连接网关推送」。 |
| **6 万连接单机的真实瓶颈是什么？** | 不是 CPU，是 **GC 和内存带宽**。每个连接两个 goroutine + 4096 缓冲的 channel（预分配 4096×16B ≈ 64KB），6 万连接光 Send channel 就是 3.8GB。所以 `SendChanSize` 不能无脑调大。 |
| **丢了 1% 的消息，用户不投诉吗？** | 弹幕是可丢弃数据，丢一条用户几乎无感。但要做「连续丢弃就断开重连」，让客户端拉历史补齐，而不是静默丢一整段时间。 |

## 五、不要说的话

| ❌ 别说 | ✅ 改成 |
|--------|--------|
| 「我的系统支持百万 QPS」 | 「下行投递峰值 150 万次/秒，口径是连接数 × 弹幕速率」 |
| 「用了 Redis 所以很快」 | 「Redis 承担跨机广播和计数，单条 Publish 约 0.2ms」 |
| 「Kafka 保证了消息不丢」 | 「Kafka 保证写入不丢，但我的消费端是 at-most-once」 |
| 「架构很完美」 | 「为了吞吐牺牲了可靠性，生产要补 Stream + 幂等 + 鉴权」 |
| 「压测是真实生产环境」 | 「WSL2 单机模拟，端口和内存是主要限制」 |

## 六、把「改进清单」变成加分项

面试最后一定会问「这个项目还有什么不足」。**这是你展示深度最好的机会**，直接说：

> 「我梳理过 13 个问题，最严重的三个是：Pub/Sub 断线丢消息、消费端 at-most-once、Kafka 写入阻塞会卡住 Manager 主循环。如果要上生产，第一步换 Redis Stream 做可回放广播，第二步把 offset 提交推迟到落库成功之后并用唯一索引做幂等，第三步把 Kafka 写入改成独立 goroutine + 有界队列，实时链路绝不等待持久化。」

这段话的信息密度，比前面所有性能数字加起来都值钱。
